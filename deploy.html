0先读懂这台服务的形态（5 条硬事实）

照着敲之前先认这五条，能省掉九成的「为什么不行」：

  1. 一个二进制，两种身份。服务器端是 jinteng serve；每个使用它的机器是一个「端」，用 jinteng init 建立自己的静息材料后通过 HTTPS 取用。没有数据库服务、没有反向代理、没有账号体系。
  2. 服务端只存密文与按端副本。每条凭据一把数据密钥（DEK），DEK 为每一个在册且未撤销的端各包一份。新登记的端不会自动拿到既有凭据——要由某台已写入的端重写一次那条凭据（§7.4，已实测）。
  3. 信任锚是人。服务端 TLS 证书首启自签（有效期 10 年），各端在 init 时人工核对并固定其 SHA-256 指纹（pin）。客户端只认这枚指纹，不校验主机名——所以证书里的域名/SAN 与访问地址不一致并不影响使用，但监听地址一旦定型就不能改（§11）。
  4. 解锁要「口令 ‖ 机器指纹」两个条件同时成立。端私钥文件被 Argon2id(口令 ‖ 机器指纹) 封存。拷走某端全部材料到别的机器 ⇒ 解不开、也签不出（这是异机取证这条）；只有口令、换了机器 ⇒ 失败。本产品没有恢复机制，忘记口令等于该端材料作废。
  5. 配对码与撤销他人只在 serve 的终端 stdin 上。服务在跑时，库被独占（bbolt 单写者），第二条进程的 jinteng pair new 抢不到写锁。所以 发配对码要么在 serve 所在终端敲一行 pair，要么短暂停服。本手册用 systemd 监管一个 tmux 会话来当那个终端——不停服、不用 FIFO（§4）。

1前置条件

项要求自查命令（在服务器上）
域名解析jinteng.ninja-sin.tech 的 A 记录指向该机网卡上真实存在的公网 IPv4getent hosts jinteng.ninja-sin.tech; ip -4 addr show（两边地址应能对上）
端口<PORT>（建议 8787）对客户端所在网络可达；云安全组放行 TCPss -lntp 起服后应看到监听行
时钟NTP 同步（签名时间窗 ±120 s，漂了就全是 stale-request）timedatectl | sed -n '1,6p'；确认 systemd-timesyncd 或 chrony 在跑
tmux≥ 3.x（管理通道靠它持有 stdin）tmux -V；缺则 apt-get install -y tmux
Go（若服务器自编译）Go ≥ 1.27，无需 CGO/usr/local/go/bin/go version
监听地址不能用通配。serve 明确拒绝 0.0.0.0 与 ::，实测报错原文：jinteng serve: 服务退出: server: 拒绝未指定地址（0.0.0.0／::，请显式写出本机可路由地址）。没有 -listen 默认绑 127.0.0.1:8787，公网部署必须显式写地址。二选一：
① 写解析到本机网卡的域名：-listen jinteng.ninja-sin.tech:<PORT>（证书 SAN 会把域名收进去，最直观）；
② 写该公网 IP：-listen <PUB_IP>:<PORT>。
若域名解析到的地址不在本机网卡上（NAT／弹性 IP 场景），两种都会 bind 失败：改绑本机真实内网地址，并在云侧做端口转发到该机——客户端照旧用域名访问即可（客户端只做 pin，不校验主机名）。

2编译与放置二进制

无 CGO、纯静态，推荐在一台构建机上交叉编译后拷过去。仓库已有 make 目标：

# 构建机（仓库根）
make build-linux-amd64 make build-darwin-amd64 make build-windows-amd64
# 产物
bin/jinteng-linux-amd64
bin/jinteng-darwin-amd64
bin/jinteng-windows-amd64.exe

服务器自编译也行：CGO_ENABLED=0 go build -o /usr/local/bin/jinteng ./cmd/jinteng。

# 放到服务器
scp bin/jinteng-linux-amd64 <SSH_ALIAS>:/tmp/jinteng
ssh <SSH_ALIAS> 'install -m 0755 /tmp/jinteng /usr/local/bin/jinteng && /usr/local/bin/jinteng | head -3'

分发前给每个文件留一个校验和，各端下载后比对（防被中间环节替换）：

sha256sum bin/jinteng-* > dist-sha256.txt
macOS 的架构别看名字猜。本项目的真机实测那台 Mac 是 Intel（uname -m=x86_64、无 hw.optional.arm64），所以用 darwin/amd64；Apple Silicon 要另出 darwin/arm64。各端先 uname -m 再取件。
Windows 的现实障碍。真机接入时实测：同一份无签名 windows/amd64 PE 在被控机的三个不同目录内都在数秒到数分钟内被 Windows 安全软件删除，登记动作赶在删除前完成、随后的取用全部拿不到输出。两条解法：给该目录加 Defender 排除项（Add-MpPreference -ExclusionPath <目录>，属系统级变更，需管理员与机主同意），或对二进制做代码签名。文档把这列为未解的分发形态问题，不是金縢的缺陷。

3服务用户与材料目录

服务端静息材料默认落在运行用户的 ~/.jinteng/，生产上改用专用目录＋专用用户：

sudo useradd --system --create-home --home-dir /var/lib/jinteng --shell /usr/sbin/nologin jinteng
sudo install -d -m 0700 -o jinteng -g jinteng /var/lib/jinteng

该目录最终会包含 5 件服务端材料，权限都要 0600：

文件是什么丢了会怎样
jinteng.dbbbolt 单文件库：密文、真名密文、按端 wrap、设备名录、配对记录、nonce 去重表全部凭据与名录消失，不可恢复
library.key服务端库密钥（32 B）：凭据名盲索引 HMAC、名字密文、配对码加密盲索引与名字密文全部失效，等同丢库
server.crt / server.key首启生成的自签 TLS 证书与私钥（SAN 冻结在生成时的监听地址）重签＝换指纹＝每台端都要重 pin（§11）
events.jsonl追加式取用事件，五字段硬白名单（ts／device_id／action／outcome／name_blind_index），不含凭据内容丢使用统计（多端使用统计的分子），不影响凭据

4systemd＋tmux 单元（发码不停服）

思路：systemd 监管 tmux 的一个专用会话，tmux 替 serve 持有那个「终端」的 stdin。发配对码＝往会话里送一行；读码＝抓面板文本。既不需要停服，也不需要手工 FIFO，进程崩溃时 Restart=always 照样生效。

写 /etc/systemd/system/jinteng.service（把两处 尖括号 换成你的值）：

[Unit]
Description=jinteng 单源凭据服务（自签 TLS ＋ v2 签名面）
After=network-online.target
Wants=network-online.target

[Service]
Type=simple
User=jinteng
Group=jinteng
Environment=JINTENG_DIR=/var/lib/jinteng
ExecStartPre=/usr/bin/install -d -m 0700 -o jinteng -g jinteng /var/lib/jinteng
ExecStart=/usr/bin/tmux -L jinteng -f /dev/null new-session -Ag jinteng "/usr/local/bin/jinteng serve -listen <LISTEN_HOST>:<PORT>"
ExecStop=/usr/bin/tmux -L jinteng kill-session -t jinteng
Restart=always
RestartSec=3
NoNewPrivileges=true

[Install]
WantedBy=multi-user.target
sudo systemctl daemon-reload
sudo systemctl enable --now jinteng
systemctl status jinteng --no-pager | head -6

管理命令统一走这个别名（-L jinteng 是私有 socket，与会话隔离；socket 目录会按用户落在 /tmp/tmux-$(id -u jinteng)/）：

alias jtmux='sudo -u jinteng tmux -L jinteng'
jtmux ls
jtmux capture-pane -p -J -S -300 -t jinteng | tail -5

直接进终端操作（人肉现场）：sudo -u jinteng tmux -L jinteng attach -t jinteng，脱离按 Ctrl-b d。

三条写法上的坑，都是实测踩到的：
  • 读面板要带 -J。终端宽度会把 64 位指纹折成两行，不拼行就提取失败。
  • 要读历史得加 -S -300（负数是回滚行数），否则只看到当前屏。
  • 别在 ExecStart 里把 serve 接管道（如 | tee）：那样会话里活下来的是 tee，serve 崩了 systemd 也看不出来，Restart=always 形同废掉。要日志就 journalctl -u jinteng（tmux 的输出会进 journal）或事后单独抓面板。
  • tmux new-session -Ag 在前台跑，配 Type=simple；会话内命令退出⇒会话结束⇒tmux 退出⇒systemd 重启。这条链就是重启保证的来源。

5首启：取证书指纹

jtmux capture-pane -p -J -S -300 -t jinteng | grep '指纹 (SHA-256)'

期望输出（实测原文，指纹值会不同）：

jinteng serve: 正在监听 <LISTEN_HOST>:<PORT>
jinteng TLS 证书已生成，指纹 (SHA-256): <64 位十六进制>

把这串指纹记进你的运维台账（它是各端 -pin 的取值）。它不是秘密——是公钥级材料；但它必须在服务端屏幕上产生并被人工抄走，因为 init 阶段的核对等于第一次信任建立（TOFU）。

首启就要按最终监听形态起服。证书 SAN 在生成时写定，之后换 -listen 的地址族会fail-closed，原文：server: 既有证书 SAN 不含监听地址 "…";本产品不自动换证书——请人工删除 server.crt／server.key 重新签发，并在各端重新核对并固定指纹（pin）。删证重签＝每台端都要重 pin（§11）。

6登记第一台端

6.1 在服务器上发一枚配对码

jtmux send-keys -t jinteng 'pair' Enter
sleep 1; jtmux capture-pane -p -J -S -300 -t jinteng | grep '配对码（一次性' | tail -1

期望：配对码（一次性，10m0s 内有效）：<32 位十六进制>。它是 128 bit 随机值，只显示一次、10 分钟内有效、用过即废；库里只存 HMAC-SHA256(library.key, 码) 的索引与加密载荷，运维误存该文件也不会泄露码本身。

6.2 在那台端上 init

jinteng init \
  -url https://<LISTEN_HOST>:<PORT> \
  -pin <64 位指纹> \
  -device <dev-id> \
  -pair <32 位配对码>

期望：jinteng: 本端材料已建立并向服务端登记。这一步在那台机器上生成 ~/.jinteng/{device.key,config.json}：两把密钥（X25519 加密 ＋ Ed25519 签名）封在 Argon2id(口令 ‖ 机器指纹) 的信封里，口令当场输入（TTY 静默读；无 TTY 时用 JINTENG_PASSFILE，指向的文件权限必须 ≤0600，或 JINTENG_PASSENV）。空口令直接被拒。

机器指纹按平台取自唯一来源：Linux／WSL2 /etc/machine-id、Windows reg query 的 MachineGuid、macOS ioreg 的 IOPlatformUUID——三端都已在真机实跑过。所以同一物理机上的 WSL2 与 Windows 是两个独立端（两条指纹渠道取值不同）。

设备 id 建议用 [A-Za-z0-9_.-]{1,64} 的简单名（它会进事件与名录；服务端硬性规则只是非空、不含 NUL，但纪律一致更好）。
登记失败的两种下场要分清。
  • 码错／过期／用过：登记被拒（invalid-pair-code），码不会被烧掉（判定与消费在同一事务），换一枚或复用未消费的码都可继续。
  • init 会先建本地材料再出网登记。若登记未确认，本地已留下 device.key，重跑会撞：client: 静息材料 device.key 已存在，拒绝覆盖（v0 无恢复机制）。此时要么删掉该端 ~/.jinteng/ 重来，要么换个 -device id。

7日常使用

7.1 命令面

jinteng put    <NAME> <value>                          # 写入／覆盖
jinteng get    <NAME>                                   # 取用并输出明文
jinteng delete <NAME>                                   # 硬删除（产品内不可恢复）
jinteng run    -e <环境变量名>=<凭据名> [-e …] <命令> [参数…]   # 注入子进程 env 后执行
jinteng devices revoke <本端 id>                         # 撤销自己那端
jinteng usage  [-window-days 30] [-out <路径>]           # 窗口达标判定／4 读数（本机，不出网）

凭据名硬规则：[A-Za-z0-9_]{1,64}（不含连字符与点），服务端在写库前把关，违反一律 bad-request。同名 put 是覆盖语义。run 会把 JINTENG_* 控制面变量从子进程 env 里剔除后再注入（实测 JINTENG_ENV_LEAK=0）。

7.2 退出码

码含义典型动作
0成功；run 全链路成功时＝被调用命令自己的退出码—
1操作失败（网络／解锁／服务端其它拒绝）看 stderr 里的服务端码
2用法错误（发生在任何解锁与联网之前）补参数
3凭据名不存在（not-found；delete 删除不存在的名字同样走 3）核对名字规则与拼写
5本端已撤销（device-revoked）见 §8.3；撤销是单向门
6该端没有这条名的副本（wrap-missing）§7.4：让写入端重写一次
7服务端不可达（ErrUnreachable）检查监听／防火墙／DNS；本产品不提供缓存值

被 run 调用的命令若自己要用非零退出码，建议 ≥10，以免与上表歧义。

7.3 一次最小旅程

# 在已登记的端上
jinteng put GIT_TOKEN ghp_xxx…            # 注意：值走 argv（见 §12 天花板）
jinteng get GIT_TOKEN
jinteng run -e GH_TOKEN=GIT_TOKEN -- gh auth status
jinteng delete GIT_TOKEN                  # 硬删除；随后 get 应得 rc=3
jinteng usage -window-days 30 | head -20

7.4 新端看不到老凭据（最容易困惑的一条，已实测）

dev-b 上 jinteng get SHARED
  → rc=6，jinteng get: client: 该端无此名的 wrap 副本（服务端码 wrap-missing）
在 dev-a 上把同一条重写一次：jinteng put SHARED 'V1'
dev-b 上 jinteng get SHARED
  → V1                                        # 实测结果

原因：DEK 的按端重包发生在 写入时（写入端从服务端名录取全部在册未撤销端）。新登记的端在此之前的任何写入都没带上它。所以每接入一台新端，把需要共享的凭据重写或轮换一次。

7.5 删除一条凭据

jinteng delete GIT_TOKEN          # 期望「jinteng: 凭据已删除」，rc=0
jinteng get GIT_TOKEN             # rc=3（not-found）

删除在服务端是单事务硬删除：该名字的密文、名字密文与该索引下全部按端封装一并移除；随后任何端取用都得到可区分的未找到。权限与写入／取用同级——任意在册且未撤销的端都可以删除已知名字，不要求调用方能解密。删除成功或拒绝都会落一条 action=delete 的五字段事件，名字只以盲索引出现；usage 的成功取用计数不受影响。

删除不可恢复。没有回收站，也没有服务端备份；若要重新使用该名字，只能重新 put。另外，「删除」指产品键空间内不可再取用，不承诺对存储介质做物理擦除（数据库空闲页可能保留旧字节）。

8管理面：发码／撤端／读数

8.1 配对码

jtmux send-keys -t jinteng 'pair' Enter          # 签发一枚（打印一次）
jtmux send-keys -t jinteng 'pair list' Enter     # 列未消费码的索引前缀与剩余时限
jtmux send-keys -t jinteng 'pair revoke <前缀>' Enter   # 作废一枚

读结果一律用 jtmux capture-pane -p -J -S -300 -t jinteng | tail -n 6。

8.2 撤销

jinteng devices revoke <本端 id>                 # 端撤自己：期望「jinteng: 设备已撤销」（实测 rc=0）
jtmux send-keys -t jinteng 'revoke <dev-id>' Enter   # 撤他端：只能在服务端终端
# 面板回显：jinteng: 端 <dev-id> 已撤销（旧 wrap 永不重包，取用面 403）

网络面上撤销别人会被拒（revoke-foreign，403），客户端更是在出网之前就拒并提示走终端——这条发起面是 2026-10-16 的裁定（撤销发起面的既有约束），动机是「一枚泄露的配对码不该换来撤销全部健康端的能力」。

8.3 撤销之后想恢复？先读这段

撤销是单向门，本手册把它写成运维约束：

  • 被撤端的旧密文副本不重包，取用面一律 403；要彻底断绝它能看到的内容，靠轮换凭据。
  • 协议上允许「同一把签名公钥」重登记恢复该 id，但当前 CLI 做不到：init 拒绝覆盖已存在的 device.key，也没有单独的重新登记命令。若那台端还活着，等于永久失去该 id。
  • 结论：撤销前先确认那台端真的退役了；需要恢复请按「新设备 id 重新登记」，并且 §7.4 重写凭据。

要一条命令完成「不重建材料、只重新登记」，需要一次小的代码改动（新增 reenroll）；那是新 change 的范围，本手册不假装它已存在。

8.4 使用读数（窗口达标判定／4）

sudo -u jinteng JINTENG_DIR=/var/lib/jinteng /usr/local/bin/jinteng usage -window-days 30

usage 只读 events.jsonl：不 unlock、不出网、不打开库（所以服务在跑也能取数）。要点两条：

  • 必须在服务端所在机取。远端自己那份 events 只有 run 没有 get，在远端跑会如实报 devices_with_success=0，那不代表使用统计未达成。
  • 取用次数与首次成功时间按服务端 get 计；run_ok 单列展示（一次 run 底下必有一条 get，双计会让使用占比 的分子翻倍）。

实测读数样例（三种都出现过）：

# 达成态（真机三端在册）
devices_with_success = 3 | criterion1_met = true
north_star = {numerator: 5, denominator: "not-observable", ratio: null}

# 未达成态（只有一台端用过）——输出会自己说明，不要美化
"criterion1_met": false
"窗口内未达标（窗口内 1 台端有成功取用，须≥2）;按 产品前提：需复核前提，如实降级为自用工具"

9备份与恢复

9.1 备份集

要备的是四件：jinteng.db、library.key、server.crt＋server.key（成对，否则重签换指纹）、events.jsonl（可选，统计用）。库是 bbolt 单文件，正在写的时候拷贝会拿到撕裂副本，所以用「一致性快照」而非 cp：

sudo -u jinteng /usr/local/bin/jinteng usage -window-days 30 -out /root/jinteng-backup/usage-$(date +%F).json 2>/dev/null
sudo systemctl stop jinteng                       # 停服取一致快照（库只有服务在写）
sudo tar -C /var/lib/jinteng -czf /root/jinteng-backup/jinteng-$(date +%FT%H%M).tar.gz .
sudo chmod 600 /root/jinteng-backup/*.tar.gz
sudo systemctl start jinteng
sudo ss -lntp | grep <PORT>                    # 回来确认在监听
备份必须离线加密。「同一个目录里的 db ＋ library.key ＋ TLS 私钥」正是本产品的已知天花板（同机同权限可还原凭据名、并可解密 TLS 通道）；把这个包原样放到同一台机器或同一个可访问域，等于把天花板搬到备份里。异地／离线＋独立密钥加密，且别把它放进任何日志外送或自动同步目录。

9.2 恢复

sudo systemctl stop jinteng
sudo tar -C /var/lib/jinteng -xzf /root/jinteng-backup/jinteng-<时间戳>.tar.gz
sudo chown -R jinteng:jinteng /var/lib/jinteng && sudo chmod 700 /var/lib/jinteng
sudo find /var/lib/jinteng -maxdepth 1 -type f -exec chmod 600 {} +
sudo systemctl start jinteng
# 端到端验证（在一台已登记的端上）
jinteng get <某条已存在的凭据名>

恢复不了的三样，先说清楚免得现场慌乱：忘记的口令（产品不存、无法重置）；被撤销端所能见的旧内容（恢复备份也不会让撤销变成未撤销——以库里状态位为准）；只备份了 db 却没备份 library.key 的情形（名字密文与盲索引解不开，等同丢库）。

10升级、换监听、重 pin

10.1 常规升级（只换二进制）

sudo systemctl stop jinteng
sudo install -m 0755 /tmp/jinteng-new /usr/local/bin/jinteng
sudo systemctl start jinteng
jtmux capture-pane -p -J -S -60 -t jinteng | tail -2      # 应只有「正在监听 …」，不该再出现「证书已生成」
jinteng usage -window-days 30 >/dev/null && echo 服务端可用

协议是 /v2 单一版本、不做版本协商（本仓没有旧客户端分发渠道）。若未来出现不兼容的线格式改动，各端要一起升级，不能只升服务端。

10.2 换监听地址／换证书 ⇒ 每台端都要重 pin

# 1) 改 jinteng.service 里 -listen 的 host，然后删旧证重签
sudo systemctl stop jinteng
sudo rm /var/lib/jinteng/server.crt /var/lib/jinteng/server.key
sudo systemctl start jinteng
NEWFP=$(sudo -u jinteng tmux -L jinteng capture-pane -p -J -S -300 -t jinteng | grep -oE 'SHA-256\): [0-9a-f]{64}' | awk '{print $2}')
echo "新指纹 $NEWFP"
# 2) 每台端改自己的 pin（材料里的 config.json 只有三个字段）
#    macOS／Linux：~/.jinteng/config.json；Windows：%USERPROFILE%\.jinteng\config.json
#    编辑 tls_pin 为 $NEWFP 后：
jinteng get <已存在的凭据名>       # 取到即证明 pin 生效；失败会明确报 pin／主机名不匹配
# 3) 若新地址在旧证书 SAN 里不存在，serve 会 fail-closed 并给出上面这段人工流程的提示

注意：重 pin 不需要重新登记（端密钥与名录都没变），也不要为此重发配对码。

# 从端上先分层定位

12已知天花板（如实标注）

  • 同机同权限能读 /var/lib/jinteng 整个目录的人，同时拿到 db 与 library.key，因此能还原凭据名；TLS 私钥也在同一目录。异机取证这条 只主张材料离开本机即失效，不主张同机不可读。
  • 值与配对码走 argv：jinteng put <NAME> <value> 与 init -pair <码> 的进程参数对本机同权限可见（ps／审计日志）。这是既有形态，不是本次部署能改的口径。
  • 没有恢复：忘记口令＝丢该端；device.key 丢了只能作为新 id 重新登记，并且重写需要共享的凭据。
  • 不做端侧缓存：服务端不可达即退出码 7。离线可用属未来新 change（与异机取证这条／3 直接冲突）。
  • 不做多用户与权限模型：一个单源，所有在册端都能取到自己有副本的全部凭据；谁可撤销谁见 §8.2。
  • 新登记端会成为可信端：配对码只授登记资格（不含任何解密能力），但登记成功的那一端会在之后的每次写入中获得 DEK 副本。所以发码＝授权一台新机器进来，请在服务端屏幕前人工抄码，不要把它接进任何自动化管道。
  • 不提供 ACME／公网 CA，也不建议套 nginx 反代（反代会接管 TLS 而使 pin 语义失效，且与「不引入外部常驻服务」的设计裁定冲突）。要改这两条属于新 change。
  • 纯后台自动化取用需要口令在场（签名与解锁同信封）。定时任务里放 JINTENG_PASSFILE 等于把双要素降为单要素——要这么用请先读 §12 第三条。
